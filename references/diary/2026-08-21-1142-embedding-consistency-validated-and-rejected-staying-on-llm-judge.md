Same session as the Elo work above. User's instinct: "if we embedded results and used distance between vectors, if that might be a more economic test that's still effective" — could embeddings replace (or cheapen) `elo.py`'s LLM-judge tournaments. Brainstormed where it fits: consistency is fundamentally "do these things say the same thing," which is exactly what embedding similarity measures — a plausible full replacement for `run_consistency_elo`, no tournament needed, just mean pairwise cosine similarity within a variant's own repeat set. Quality is a different question ("which is better," not "how similar") that embedding distance can't answer directly — stayed LLM-judge-only there, embeddings floated only as a possible cost-reduction pre-filter on which pairs are worth a judge call, not attempted this session.

**Model selection took several real corrections before landing anywhere.** First pick (`nomic-embed-text-v1.5`) was rejected on sight — "I really don't want an opinionated RAG focused one... good for general comparisons for downstream tasks like classification" — a fair catch: nomic/bge/e5-style models are trained on an asymmetric query-vs-passage retrieval objective (mandatory `search_query:`/`search_document:` prefixes are the tell), a different notion of similarity than symmetric "do these two peer answers agree." Pivoted to `all-mpnet-base-v2` (the original Sentence-Transformers general-purpose flagship, STS/NLI-trained, no retrieval framing), then immediately over-claimed a tradeoff that wasn't real: "no good general-purpose one that fits the context?" caught that short context (384 tokens) isn't inherent to being general-purpose, just a 2021-era artifact of that specific model's position embeddings — newer general-purpose models (`Alibaba-NLP/gte-large-en-v1.5`, `jina-embeddings-v3`) support 8192 tokens without being retrieval-tuned. Landed on `gte-large-en-v1.5` on that basis, checked real hardware (MacBook Air M2, 16GB RAM comfortably sufficient; disk was the actual constraint — 17.9GB free at first check, downgrading the pick to `gte-base-en-v1.5`; re-checked after the user cleared space to 106.4GB free, upgrading back to the `large` variant since disk was no longer binding).

**Then it turned out to be broken.** Built `embeddings.py` (plain-Python cosine similarity/mean-pairwise-similarity/Spearman correlation, zero dependency on `sentence_transformers`/`torch` except in one lazily-imported function, so the module stays importable without the heavy optional extra) and a new `embed-consistency` CLI command that re-reads an existing `elo` run's stored repeat answers and Spearman-correlates an embedding-based consistency ranking against that run's own real LLM-judge consistency Elo ranking — the actual validation methodology, borrowed directly from the Sort-MST paper's own evaluation approach. First real run hit a genuine bug: `gte-large-en-v1.5`'s custom (`trust_remote_code`) RoPE implementation threw a reproducible `IndexError` — the same garbage index — on both MPS and CPU, even embedding a single two-word string. Not a batching issue, not Apple-Silicon-specific: a real incompatibility between that specific model revision and the installed `sentence-transformers`/`transformers` versions. Pivoted to `all-mpnet-base-v2` (stock architecture, no custom code, guaranteed to work) — trading back the truncation risk that had just been argued against, but reliability won given the goal was to actually get a measured answer, not the theoretically-best model.

**Also found a real, unrelated bug along the way**: `_answers_by_variant` silently returned an empty pool for every step when fed records read back from disk via `results.read_result` — JSON round-tripping turns `step_answers`' int keys into strings, and the lookup only checked the int form. No exception, just quietly wrong output; `elo_cmd` never hit this because it always uses fresh in-memory records, never disk-read ones. Fixed to check both key forms, with direct unit tests (this is a small pure function, unlike `elo_cmd`'s concurrency-heavy job scheduling which has never had direct tests — no excuse not to test this one).

**The actual result, once everything worked**: ran the correlation against both real stored `elo` runs (6 step-level observations total). Mean Spearman rho ≈ **-0.17** — 4 of 6 steps negative, only 2 positive. Embedding-based consistency does not reliably track the LLM judge's consistency verdict, and if anything leans slightly anti-correlated in this sample. Plausible (unconfirmed) explanation: embeddings likely capture topical similarity ("both about `validator.py`/`ahar` CLI") rather than the finer-grained factual agreement the judge actually scores (do the answers name the same specific implementation, or subtly disagree on which is primary) — two answers can be topically near-identical while disagreeing on exactly the claim that matters. `all-mpnet-base-v2`'s 384-token truncation is a real, unisolated confound too. Sample is small (n=3 competitors per step is coarse; 6 total observations is thin).

**Decision: stay on LLM-as-judge for `run_consistency_elo`.** This first validation argues against trusting embedding-based consistency as a replacement, and the whole point of running the correlation check before building further on it was to catch exactly this rather than assume the intuition held. `embeddings.py` and `embed-consistency` stay in the codebase as real, tested, working infrastructure (144 unit tests, two genuine live-found bugs fixed) — not wasted, just not (yet) trusted enough to replace anything. Revisit if: the truncation hypothesis gets isolated and ruled in or out, a bigger sample changes the aggregate correlation, or the cost-reduction-pre-filter idea for quality (never attempted this session) turns out to be worth trying on its own separate merits.
