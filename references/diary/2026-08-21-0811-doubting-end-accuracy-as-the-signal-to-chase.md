User reflection, prompted by digging through two `real-repo-exploration/question-set-3` runs today: "I wonder if I'm barking up the wrong tree here. Accuracy is not a big problem for any of these approaches, and evaluation of accuracy is very very hard."

The evidence for the first half goes back further than today. `question-set-1`'s live results (`methodology.md`, "What a full, real run actually produced") show all three conditions — `full-harness`, `metaskill-removed`, `harness-removed` — landing on `end_accuracy: 1.0`, differentiated only by `tokens`/`wall_clock_seconds` (18,648/92.6s vs. 51,765/198.5s vs. 61,037/205.8s). `question-set-3` today told the same story from the other side: neither of its two check failures held up as a real capability gap on inspection. `full-harness`'s step-3 miss (didn't mention `ahar-visualizer`'s activity-overlay legend) traced to prompt ambiguity — "the tree" collided with the harness-summary tree the priming turn had just rendered — not routing/metaskill making it worse at finding things. `metaskill-removed`'s step-1 miss, new on the second run, traced to sampling variance alone: same variant, same fixture, same cold search, and the first run went one `find` deeper into `harnesses-ref/validator.py` while the second stopped at `ahar validate --help` and answered from the CLI wrapper instead — both defensible, only one matched the check's specific expected noun.

That's not a new pattern either — it's the fourth or fifth time a check failure in this project has turned out to be a check-design problem rather than a real answer-quality gap: the line-broken source-quote check (`2026-08-20-1032`), the three-iteration chase to find one check value robust to legitimate rephrasing (`2026-08-20-1600`), and now today's two. Meanwhile `tokens`/`wall_clock_seconds` (and now, as of this session, the `input_tokens`/`output_tokens` split within `tokens`) have never once needed a redesign to keep meaning what they say — every number's story has held up under transcript-level scrutiny every time it's been checked.

Not a decision, just naming the doubt before it's lost: if `end_accuracy` keeps costing check-design iteration for a signal that hasn't yet shown a single stable, reproducible gap between harness conditions on real content, it may be the wrong place to keep investing — the actual differentiator this project keeps finding, run after run, is cost and speed, not correctness. Open question for a future session: what would `end_accuracy` need to look like (RepoProbe's weighted/tiered checklist grading, sourced from real pre-existing answers rather than hand-written rubrics? dropped as a headline metric entirely, kept only as a sanity floor?) before it's worth the same confidence the cost/time metrics already have.
