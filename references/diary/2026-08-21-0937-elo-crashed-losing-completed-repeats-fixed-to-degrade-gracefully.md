Found live, first real attempt at generating actual results: `traversal-compare elo real-repo-exploration/question-set-3 --times 4 --max-parallel 4` crashed with `InteractiveSessionError: timed out waiting for turn 1 to complete` on the 4th of 4 concurrent repeats' harness-priming call, after 3 repeats had already completed successfully. Root cause of the timeout: `--max-parallel 4` on a 3-variant question set means up to 12 concurrent `claude` processes (each repeat run internally runs every variant concurrently too — the same multiplier `batch`'s own docs already warn about, which this command's `--max-parallel` help text never mentioned), plausible resource contention on one machine.

But the timeout wasn't the real problem — `elo_cmd`'s error handling was. `_job`'s loop called `future.result()` directly inside `for future in as_completed(futures)`, so the first exception propagated immediately and crashed the whole command, discarding the 3 repeats that *had* completed (real, paid-for `claude` cost, thrown away for nothing). This was a deliberate choice made when the command was first built (`2026-08-21-0842`'s commit message reasoned "one failed repeat here corrupts the whole comparison pool ... surface it immediately rather than silently continuing with a thinner pool") — reasonable-sounding in the abstract, wrong in practice: `batch` already solved this exact problem (catch per-job exceptions, keep going, report failures, exit nonzero) and `elo` should have matched it instead of re-deriving a worse answer.

Fixed to match `batch`'s pattern: `_job` failures are caught and collected, not re-raised; the run proceeds with whatever repeats completed; a summary of failures prints before the tournaments run; the command still exits nonzero if anything failed (so a degraded run isn't silently invisible), but only hard-errors if fewer than 2 repeats survived (genuinely nothing left to compare). `--max-parallel`'s help text now states the `3x` multiplier explicitly, matching what `batch`'s skill doc already said. No new unit tests — this is `cli.py` job-scheduling/error-flow, the same category `batch_cmd`'s equivalent logic has never had direct unit tests for either, tested by running it for real instead. 122/122 unit suite still passes (untouched).
