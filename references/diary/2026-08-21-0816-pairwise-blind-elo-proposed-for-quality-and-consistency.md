User's proposal: replace (or run alongside) checks-based `end_accuracy` with **blind pairwise LLM-judge comparison, Elo-scored**, for two distinct properties — answer quality, and cross-run consistency — both scored "irrespective of checks" (no rubric, no answer key handed to the judge) and "with complete ignorance" (the judge doesn't know which harness condition or which run produced either side of a comparison), presented in random order to cancel position bias.

**Mechanism sketch, grounded in what exists today.** `grading.py`'s current judge is a single call per variant: handed that variant's own `step_answers` plus a bounded `diff_summary` against the pristine fixture, no tool access, no sandbox path — it reasons only over what's placed directly in the prompt (see the module's own docstring, "score what was produced, don't re-derive it independently"). A pairwise judge keeps that same discipline but changes the shape of the call: instead of one variant's answers plus a rubric, it gets exactly two anonymized answers to the same question (labels like "Answer 1"/"Answer 2" only, order randomized per call so position never correlates with variant or recency) and a comparison prompt with no rubric text and no mention of harness conditions, routing, or the standard at all — just the original question and the two candidate answers, asked which better/more-accurately addresses it (or, for consistency, whether they agree on the core claims).

- **Answer-quality Elo.** Pool every answer collected for one question (a `step_id`) across every variant and every repeat run in a `batch`. Sample random pairs from that pool, run each through the blind pairwise judge, and feed win/loss (or tie) into a standard Elo update. After enough comparisons, each individual answer has an Elo rating; roll up to a per-variant mean (or win-rate) as the reported quality signal for that question, in place of — or alongside — `end_accuracy`. This is close to Chatbot-Arena-style preference judging, which the field already trusts more than absolute LLM self-scoring for exactly the reason motivating this: models are more reliable at "which of these two is better" than "rate this 1–10" or "does this pass rubric item N."
- **Consistency Elo.** Reframed once during design, because Elo needs a competitive win/loss and "does the model say the same thing twice" isn't naturally a property of a single answer — it's a property of a *set* of repeat runs. So the competitors here are continuums (a variant's whole set of repeat-run answers to one question), not individual answers, matching what the user actually described: "one continuum vs another, which is the most consistent." A comparison shows the blind judge a small anonymized sample (e.g. 3) from continuum A's repeats side by side with continuum B's, order randomized, and asks which set shows more internal agreement on the core information — not which is more correct. Elo-rank continuums (effectively: variants, or variant×fixture-revision if that ever varies) against each other on that property. This directly tests something checks have never measured here: whether harness support makes answers more *stable* across runs, independent of whether any single run is right.

**Real costs and gaps, named rather than glossed over** (matching this project's own pattern of naming blockers directly instead of discovering them mid-build):
- `batch` today only aggregates scalars (mean `tokens`/`wall_clock_seconds`/`end_accuracy`) — it doesn't retain a poolable structure of every run's own `step_answers` across repeats. That pool is the actual prerequisite for either mechanism; building it is the real first step, not the Elo math itself.
- Comparison count doesn't stay small: a full round-robin over an n-answer pool is O(n²) judge calls; even a sampled/iterative Elo update (the usual real-world compromise) needs meaningfully more judge calls than today's one-call-per-variant grading pass. Each comparison is a real LLM call with a real token cost — this is a genuine new expense layered on top of the run cost this session just finished splitting into input/output, not a free upgrade.
- Blindness is harder to guarantee than "don't show the label." An answer can self-reveal the condition that produced it — a with-harness answer saying "per `SKILLS.md`..." or naming the metaskill, a without-harness answer describing a `find`/`grep` trail a routed answer wouldn't need — the same self-revealing-decoy problem this project already hit designing fixtures (`2026-08-20-0057`). Redacting that reliably before the judge sees it is unsolved, not just unbuilt.
- Still open: how many comparisons are "enough" per question before the Elo numbers are stable rather than noisy from too few matchups, especially at `batch`'s realistic repeat counts (single digits, not hundreds).

Not yet scoped or built — accuracy checks stay as-is for now. This entry exists so the mechanism doesn't have to be re-derived from scratch next time it's picked up, and so the real costs (pool-building work, judge-call count, self-revealing answers) are visible up front rather than found the hard way mid-implementation.
