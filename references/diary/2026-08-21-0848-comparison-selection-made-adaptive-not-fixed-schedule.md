Follow-up to `2026-08-21-0842-elo-mechanism-built-and-verified-live.md`, same session. User's question — "shouldn't Elo be efficient to comparison samples?" — caught a real gap in the first cut: `elo.py`'s comparison selection (`_sample_pairs`) computed a *fixed* schedule before any rating existed (full round-robin for a small pool, a uniform-random subset once round-robin would exceed the target budget). That's not what makes Elo worth using over a fixed rubric in the first place — ratings propagate transitively, so a well-*targeted* sparse set of comparisons should rank a pool nearly as well as full round-robin, without spending a fixed schedule decided blind to what's actually still uncertain.

Replaced with adaptive selection (`elo._next_pair`, `elo._comparison_budget`): the total comparison budget is unchanged (still capped at `comparisons_per_item` matchups per competitor on average, never more than full round-robin), but which comparisons run within that budget is now chosen one at a time, after each prior comparison's rating update — prioritizing pairs not yet compared, weighted toward whichever competitors have the fewest comparisons so far (so a limited budget can't starve one competitor of comparisons the way a uniform random sample could by chance), tie-broken toward competitors closest in current rating (a comparison between two already-clearly-separated competitors teaches little, so a limited budget shouldn't spend itself there). This is genuinely sequential now — each pick depends on the outcome of every prior one — which is also what makes the adaptivity possible at all; the earlier fixed-schedule version could equally well have picked all its pairs before running a single comparison.

7 new/rewritten unit tests directly target the two properties this was about: no competitor gets zero comparisons under a budget well below full round-robin (`test_run_quality_elo_with_budget_capped_below_round_robin_still_covers_every_competitor`), and no pair gets compared twice within a budget that fits inside round-robin (`test_run_quality_elo_never_compares_the_same_pair_twice_within_its_round_robin_budget`), plus direct tests of `_next_pair`'s tie-breaking order. All 119 tests pass. Not re-verified live on top of the earlier live run — this is a targeted algorithmic fix to comparison *selection*, not to the judge call or the Elo math itself, and the unit tests exercise exactly the properties that changed; spending another real judge-call budget to re-confirm it felt like the wrong tradeoff given this project's own repeated cost concerns about judge-call volume.
